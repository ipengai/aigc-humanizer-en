# `turnitin_fit_detector_v2` 分档与改写路由改造方案

> 状态：本地模型、首轮路由、低覆盖率重聚合、模型常驻、归因后二次定向改写、订单记录和回归测试已实现
> 目标：以 `turnitin_fit_detector_v2`（模型版本 v2.1.0）作为低成本的第一层检测器，根据风险档位选择改写链路，减少不必要的付费 API 调用。

本文统一使用 `turnitin_fit_detector_v2` 作为 detector 名称；`v2.1.0` 只表示该 detector 当前加载的模型版本，不再把“turnitin_fit_detector_v2”单独作为产品或适配器名称。

## 1. 背景与边界

实验中 `turnitin_fit_detector_v2`（模型版本 v2.1.0） 使用 83 项段落及邻段上下文特征，输出段落概率，再按段落词数加权为 `risk_percent`。在 22 篇样本上，Huma 改写后的 `turnitin_fit_detector_v2` 平均风险分为 18.9，LyNote 全文翻译链为 37.3，Blader 为 58.2，Harshaneel 为 62.3；这说明 `turnitin_fit_detector_v2` 适合作为 Turnitin 导向的本地预筛和改写后复检信号。

`turnitin_fit_detector_v2` 仍然是**实验性本地风险分**，不是 Turnitin 官方 AI 率，也不能用于证明作者身份或学术不端。当前训练数据只有 324 个 trusted 段落、6 篇文档和 5 个来源组，必须同时保留 `coverage` 和模型版本；当前统一使用 `V2_REJECT_COVERAGE=0.60`。首次自然段检测覆盖率低于该值时，必须先按正文结构执行一次检测专用重聚合；重聚合后仍低于该值，才进入 `needs_review`。

本方案只解决两件事：

1. 把 `turnitin_fit_detector_v2` 接入线上应用作为本地第一层检测器，避免所有文本先调用 Sapling 付费 API。
2. 按风险档位选择“不改写、低成本翻译链、Huma 付费/LLM 链路”，并在改写后复检。

Sapling、aidetector.com 等外部检测器继续作为抽样校准和客户指定平台，不与 `turnitin_fit_detector_v2` 分数直接平均。

## 2. 目标路由规则

## 2.0 与现有 Sapling 模式的兼容关系

这次改造不把 Sapling 路径和 `turnitin_fit_detector_v2` 路径硬编码成两套任务系统，而是统一成三层：

```text
Detector（检测器）
  ├─ sapling
  ├─ originality
  └─ turnitin_fit_detector_v2
        ↓
Routing policy（路由策略）
  ├─ legacy_whole_document
  └─ risk_band_segmented
        ↓
Humanizer provider（改写器）
  ├─ ai_text_humanizer / huma
  ├─ llm_based
  ├─ translation / lynote
  └─ rule_based
```

现有线上模式可以原样保留：当 `AI_DETECTOR_ADAPTER='sapling'` 或订单策略为 `legacy_whole_document` 时，继续执行当前“全文 Sapling → 现有改写器 → 改写后 Sapling”的逻辑，不启用风险分段路由，也不改变历史订单的口径。

新模式只需要选择：

```python
AI_DETECTOR_ADAPTER = "turnitin_fit_detector_v2"
REWRITE_ROUTING_POLICY = "risk_band_segmented"
```

两种模式共用文件解析、`low / median / high` 切分、主备调用、进度上报、订单落库和 DOCX 回填。差异仅在于：检测器如何返回分数，以及路由策略如何决定每个改写块使用哪个 provider。这样可以按配置、用户类型或灰度比例切换，出问题时回退到 `legacy_whole_document`。

需要避免把 Sapling 误当成改写器：Sapling 是检测 provider；真正的改写 provider 仍然是 Huma、LLM、翻译链或规则链。订单记录中分别保存 `detector_backend`、`routing_policy` 和 `actual_chain`，不能只用一个 `rewrite_method` 字段表达三者。

### 2.1 档位定义

| `turnitin_fit_detector_v2` 全文风险分 | 路由 | 目标 | 付费 API 预算 |
|---:|---|---|---|
| `< 20` | `protect`：原文直出 | 低风险文本不做激进改写，避免把人写内容改出 AI 味 | 0 |
| `20–60` | `low_cost_first`：先走 LyNote/翻译链 | 优先使用 EN→ZH→EN 等低成本链路；复检仍未达标时再调用 Huma | 默认 0，失败才 1 次 Huma |
| `> 60` | `segment_route`：长文按段落分流，短文 Huma 全量 | 长文只深度处理高风险块；中风险块先走低成本链，低风险块保护 | 按段落实际命中计费 |

边界采用左闭右开：`20` 进入 `low_cost_first`，`60` 仍属于 `low_cost_first`，`60.01` 进入 `huma_first`。风险分缺失、文本过短，或经过一次检测专用重聚合后覆盖率仍低于 60% 时进入 `needs_review`，不自动选择激进改写器。

### 2.2 低成本链路的失败条件

20–60 档先调用翻译链，满足以下任一条件即升级 Huma：

- 翻译链调用失败、超时或返回文本为空；
- 改写后 `turnitin_fit_detector_v2` 风险分没有下降至少 5 个百分点；
- 改写后仍高于或等于 20%，尚未达到最终目标；
- 输出词数偏离超过 25%，或段落数/标题边界无法回填；
- 改写后首次检测 `coverage < 60%` 时先执行检测专用重聚合；重聚合后仍低于 60%，无法得到可信复检结果。

低成本链路只允许一次；升级 Huma 时复用已完成的翻译结果作为输入，避免重新处理原文。首轮组合策略结束后仍未达到全文目标时，不继续无条件调用 Huma，而是进入第 3.3 节的“归因 + 定向二改”闭环。

## 3. 检测与分段顺序

采用“先全文分档、按需结构化分段、最后改写后复检”的顺序：

```text
解析文件
  ↓
`turnitin_fit_detector_v2` 全文检测（风险分 + coverage）
  ↓
低于20：原文直出
20–60：翻译链 → `turnitin_fit_detector_v2` 复检 → 不达标才 Huma
高于60短文：结构化分段 → Huma 全量 → `turnitin_fit_detector_v2` 复检
高于60长文：结构化分段 → 段落 `turnitin_fit_detector_v2` → 按段落风险分流 → 合并 → 全文 `turnitin_fit_detector_v2` 复检
  ↓
合并回原结构
  ↓
`turnitin_fit_detector_v2` 全文复检 + 段落结果记录
  ├─ <20：完成
  └─ >=20：本地归因 → 选择少量高贡献块 → 低成本 LLM 定向二改 → 小批次全文复检
```

不建议所有文本都在全文检测前逐段检测：短文会增加覆盖率噪声，且段间上下文特征容易被截断。全文分档先决定是否值得进入段落级路由。对于高风险长文，全文分数只是“需要继续拆解”的信号，随后再做段落 `turnitin_fit_detector_v2`；对于短文，直接 Huma 全量更稳定。

### 3.1 结构化分段规则

- DOCX/PDF/TXT/Markdown 继续复用现有 `extract_text` 节点和 `source_body_indexes`；标题、参考文献、代码、图片和超链接保护节点不进入改写。
- 普通正文按现有聚合器生成逻辑块；保留 `block_id`、`source_node_ids`、`source_body_indexes`。
- 自然段首次检测 `coverage < 60%` 时，按原顺序将同一正文区域内相邻短段聚合为检测块：目标至少 40 词、最多 250 词，并优先在句末结束。标题、参考文献、代码、表格、图片和超链接等保护节点是硬边界，不与正文合并。
- 检测专用聚合只生成 `detector_block_id` 和原节点映射，不改变改写器使用的 `block_id`、low/median/high 分段、原文段落、标题位置或 DOCX 回填边界。不能为了提高覆盖率修改既有改写内核。
- 重聚合成功后以整套重聚合结果替换首次结果，不能把两次概率混合平均。结果同时记录 `raw_coverage`、`effective_coverage`、`aggregation_strategy=structured_short_paragraph_join` 和检测块映射；路由只读取 `effective_coverage`。
- 高风险长文中的单个改写块无法独立评分时，优先查找覆盖该块的检测聚合块；仍不可评分才记录 `detector_source=document_fallback` 并继承可信的全文档位。
- 段落级 `turnitin_fit_detector_v2` 只在高风险长文或二次定向改写时启用，用于排序和选择链路；文档最终分数仍使用段落概率按词数加权，不能把 0/1 标签词占比当成 AI 率。

### 3.2 高风险长文的段落级路由

默认将 `word_count >= 1000` 或正文逻辑块数 `>= 6` 的高风险文档视为长文。实际阈值应通过影子运行校准，不能只按字符数硬切。

段落 `turnitin_fit_detector_v2` 检测使用模型自身的邻段特征。低于最小词数的块无法独立评分时，不改变既有改写分段，沿用可信的全文档位并记录低置信来源。

高风险长文的首轮分流：

| 段落 `turnitin_fit_detector_v2` 风险分 | 段落动作 |
|---:|---|
| `< 20` | `protect`：原样保留，不调用改写器 |
| `20–60` | `low_cost_first`：先走翻译链；复检不达标再升级 Huma |
| `> 60` | `huma_first`：调用 Huma 深度改写 |

处理结束后重新拼接全文，再跑一次全文 `turnitin_fit_detector_v2` 并记录结果。全文已经低于 20% 时直接完成；仍未达标时进入受次数、词数和费用上限约束的定向二改，不再把所有超标块无条件重跑。
- P09/P20 这类极短文本无法稳定检测时，保持 `needs_review`，不自动触发付费改写。

### 3.3 首轮未达标后的归因与定向二改

二次改写采用“**规则负责解释与编排，低成本 LLM 负责文字重写**”的组合。现有纯规则改写在 21 篇 Huma 输出上的实验从 13 篇达标降到 11 篇、没有救回失败样本，因此纯规则不能直接承担正文二改；规则层只负责选择块、保护内容、把归因转换为经过验证的提示词指令，以及控制停止条件。

```text
首轮组合策略完成
  ↓
全文 v2 复检
  ├─ <20：完成
  └─ >=20 且 coverage可信
       ↓
     本地决策路径归因
       ↓
     归因规则映射为定向提示词
       ↓
     选择预计收益最高的 2 个块
       ↓
     低成本 LLM 二改 + 内容保护校验
       ↓
     拼回全文并重新检测
       ├─ <20：完成
       └─ >=20：在预算内处理下一批；预算耗尽则保留当前最佳结果
```

#### 块选择与停止条件

设当前可信全文风险分为 `S`，目标为 `T=20`，待降低量为：

```text
required_reduction = S - T
```

某块完成二改后的实际加权降低量为：

```text
actual_gain_i = (score_before_i - score_after_i) × words_after_i / document_words_after
remaining_reduction = remaining_reduction - actual_gain_i
```

其中 `score_before_i` 和 `score_after_i` 必须来自二改前后两次**完整文档检测**中映射到该块的结果，不能使用脱离邻段上下文的单块检测分数。该累计值用于进度估算和下一批选择，不能单独作为完成判据。原因是改写会改变段落词数权重，而模型的前后邻段特征也会随之变化。每批完成后必须按原结构拼回全文，并以最新一次可信全文 v2 分数 `<20` 作为唯一自动停止条件。

当前每轮选择 2 个块，默认最多 2 轮。第 1 轮后仅当当前最佳全文分数处于 `[20%, 30%)` 时执行第 2 轮；`>=30%` 时停止，避免对距离目标较远的文本重复产生低收益调用。同一块再次尝试时基于当前最佳版本和上一轮实测缺口生成。块排序使用“预计可降低概率 × 块词数权重”，不是只按段落风险分排序。每轮生成后都拼回全文复检，只有全文分数严格下降才接受；未改善则回退到当前最佳版本。每轮完整耗时写入 `rewrite_route_trace.steps[].duration_ms`。
如果第一轮后仍未达标，第二轮提示词会携带上一版实测的特征缺口，例如“功能词比例为 0.29，仍低于 0.34–0.40”，并继续强调保护低风险特征，避免在确定性较强的模型上重复生成同一个候选。若全文分数上升，仍回退到当前最佳版本。

#### 归因到提示词的边界

归因输出模型在本次决策路径中使用的特征。`AttributionPolicy` 不根据单个特征假设分数单调，而是把可信特征转换为有限指令；对于已经用实验确认目标区间的四项特征，同时给 LLM 当前实测值与目标区间，最终是否接受仍只由完整文档 V2 复检决定：

| 特征组 | 可执行指令 |
|---|---|
| 平均词长、长词、名词化 | 保留必要术语，简化非专业表达，优先使用动作明确的动词 |
| 句长均值、离散度、重复句首 | 调整句子长短和开头方式，重组从句关系 |
| 功能词、连接词、情态词、缓和词 | 减少模板化衔接，按语义重新组织过渡 |
| 破折号、分号、逗号等标点 | 重组句子，禁止仅机械替换标点 |
| 词汇多样性、hapax、重复词组 | 允许核心名词自然复现，避免为每次出现强行更换同义词 |

提示词同时携带两类特征：最多 3 个主要推高特征用于指定改写方向，以及最多 3 个当前正在压低分数的保护特征，明确约束 LLM 不得破坏。不可修改实体清单、数字、引用、公式、标题及段落映射仍由规则层提取并在输出后校验。校验失败或全文复检未改善时，丢弃候选并保留当前最佳结果。

提示词策略 v3 进一步把数值区间改成模型容易执行的操作：按当前篇幅给出最低功能词数量，自动抽取 5 个源文核心词并要求在同一对象再次出现时复用原词，限制一次性同义词和低频词，引导模型先核对原文原子事实，再检查词数、保护值和特征目标。该策略不增加默认 LLM 调用次数，仍为最多 2 轮。P16 的 Huma 版本曾在一次真实 DeepSeek 调用中由 `31.98%` 降至 `18.62%`，但随后 5 篇批量复跑时 P16 只降到 `25.14%`，说明单候选生成存在明显随机波动，不能用一次达标推断稳定达标率。5 篇明细见 [`experiment/v2_targeted_v3_batch/report.md`](../experiment/v2_targeted_v3_batch/report.md)。

归因脚本和完整方法见[`v2归因方法与5篇失败样本分析`](v2归因方法与5篇失败样本分析.md)。线上只保存用于审计的前 3 个特征组及提示词策略版本，不保存完整逐树路径。

## 4. 具体代码改造

### 4.0 内外两层架构（核心原则）

本次改造不重写现有改写内核，而是在外层增加一次全文 `turnitin_fit_detector_v2` 筛选，并在现有改写块上增加路由判断：

```text
全文输入
  ↓
外层：`turnitin_fit_detector_v2` 全文快速筛选
  ├─ <20：直接返回原文，不进入改写内核
  ├─ 20–60：进入改写内核；每个改写块先走低成本链，失败再升级 Huma
  └─ >60：进入改写内核；长文先对改写块做 `turnitin_fit_detector_v2`，再按块风险选择链路
                ↓
现有内核：low / median / high 切分、保护节点、请求聚合、格式回填
                ↓
每个已切好的改写块：`turnitin_fit_detector_v2` 风险 → protect / 翻译链 / Huma
                ↓
全文合并 → `turnitin_fit_detector_v2` 复检
  ├─ 达标：结束
  └─ 未达标：归因策略 → 2块一批的低成本 LLM 定向二改 → 全文复检早停
```

现有 `low`、`median`、`high` 的含义保持不变：它们继续决定正文如何聚合、每块包含多少段、如何处理最小字符数和 DOCX 位置回填。`turnitin_fit_detector_v2` 不参与重新切分，只消费这些已经生成的 `block_id` 和段落边界，并为每个块选择 `protect`、翻译链或 Huma。这样可以把检测策略和文档结构处理解耦，降低改造风险。

Huma 大块调用不再要求返回段落数与输入严格相等。返回后由 DOCX 对齐层按原顺序、文本相似度、数字覆盖和 `body_index` 建立 `1→1`、`1→多`、连续正文 `多→1` 映射；Huma 删除的标题、图注和短结构标签从源文恢复。对齐结果在进入 Word 渲染器前归一为一个源段落槽位对应一个结果，因此不改变既有图片、表格和样式骨架。`body_index` 间隙视为图片、表格或其他布局边界，禁止跨界合并；普通正文缺失或低置信映射继续使用原有局部回退。

对全文 `<20` 的文本直接跳过改写内核；对全文 `20–60` 的文本仍进入内核，但默认先让每个可改写块尝试低成本链；对全文 `>60` 的长文，在内核已经切出块后再做块级 `turnitin_fit_detector_v2` 路由。短文不强制块级 `turnitin_fit_detector_v2`，直接沿用 Huma 全量首轮，避免短文本概率噪声放大。

### 4.1 新增本地 `turnitin_fit_detector_v2` 适配器

新增 `app/ai_detector/turnitin_fit_detector_v2.py` 作为适配器边界，并在 `app/ai_detector/adapter.py` 中懒加载实际模型实现，职责：

- 调用项目内 `app/ai_detector/vendor/turnitin_fit_detector_v2/random_forest_detector.py` 的稳定 Python 接口；禁止通过子进程解析人类可读日志作为线上协议。该目录同时固定保存模型元数据和 `joblib` 文件，线上运行不依赖外部 `aigc_detector_model` 仓库。
- 返回统一结构：

```json
{
  "backend": "turnitin_fit_detector_v2",
  "model_version": "v2.1.0",
  "ai_score": 37.4,
  "risk_percent": 37.4,
  "coverage": 0.94,
  "confidence": "high",
  "paragraphs": [],
  "evidence_level": "experimental_local_estimate"
}
```

- 对模型不存在、依赖缺失、输入过短、覆盖率过低提供明确错误码；不得静默返回 50 分占位值。
- 记录文本哈希、词数、段落数、模型版本，便于复现和缓存。
- 提供 `detect_text()` 和 `detect_blocks()` 两个入口，共用同一个已加载分类器；块级检测必须一次构造矩阵并批量推理，不能循环读取模型文件。

#### 模型生命周期

当前 vendor 的 `detect()` 每次调用都会执行 `joblib.load()`。本地实测中，包含模型读取的单次检测约 116–151ms，模型已加载后的同批预测约 32–33ms，因此必须把缓存对象从“模块和路径”升级为“模块、元数据和分类器实例”。

- 每个 Web/worker 进程首次使用时在锁内懒加载一次模型，后续请求复用同一只读分类器；不得按订单、段落或检测阶段重复读取 `joblib`。
- 应用启动后可执行一次不含用户文本的 warm-up，使首次真实订单不承担模型加载和底层初始化时间。
- 多 worker 部署按“每个 worker 一份模型实例”估算内存；第一版不引入跨进程模型服务。支持服务器预加载时可以利用操作系统写时复制，但不能依赖它保证只占一份内存。
- 模型文件升级通过发布和进程重启完成，不在请求中检查文件变化或热替换，保证一个订单内模型版本固定。
- 加载失败缓存明确的初始化错误并进入既有检测失败处理；不得在每个请求中反复尝试读取损坏模型。

### 4.2 扩展检测器工厂与配置

修改 `app/ai_detector/adapter.py`：

- 新增 `turnitin_fit_detector_v2` 和 `turnitin_fit_detector_v2_mock`；保留 `sapling`、`originality` 兼容旧订单。
- `AI_DETECTOR_ADAPTER='turnitin_fit_detector_v2'` 时，`/api/analyze` 默认不产生 Sapling 费用。
- 仅保留 `V2_REJECT_COVERAGE=0.6` 一个运行阈值；模型脚本和模型文件固定随项目发布，不需要额外路径配置。
- 线上默认先用 `turnitin_fit_detector_v2`；外部 Sapling 只在用户明确选择、抽样校准或 `turnitin_fit_detector_v2` 不可用时调用。

### 4.3 接入分析接口和缓存

修改 `app/routes/analysis.py` 和 `app/helpers/tasks.py`：

- `/api/analyze` 返回 `analysis.risk_level`、`analysis.coverage`、`analysis.route` 和 `analysis.evidence_level`。
- 继续按文本哈希做进程内原文检测缓存，同时把精简检测摘要写入登录会话，供多请求链路中的扣费判断复用；应用切换检测器时通过重启清空进程缓存。
- 保存解析节点，供后续段落级路由复用；首次检测不调用改写器。
- 检测结果缓存键至少包含规范化文本哈希、模型版本和聚合策略版本。自然段结果覆盖率不足后产生的结构化聚合结果使用独立缓存键，避免与旧口径混用。

### 4.4 新增路由决策与编排模块

新增独立目录 `app/pipeline/`，不把路由放进 `app/humanizer/`。目录职责如下：

- `app/ai_detector/`：检测器适配和检测结果标准化；
- `app/humanizer/`：各改写 provider、low/median/high 分段和格式回填；
- `app/pipeline/`：风险判断、改写方法选择、检测与改写的执行编排；
- `app/helpers/`：缓存、进度、数据库和其他通用支持。

其中 `app/pipeline/router.py` 只做纯函数决策，便于单元测试；`app/pipeline/orchestrator.py` 负责按决策调用 detector 和 humanizer：

```python
    # protect | low_cost_first | huma_first | needs_review
```

路由函数不直接调用 API，只返回：

- `risk_band`
- `planned_chain`
- `reason`
- `requires_segment_detection`
- `max_paid_attempts`

`tasks.py` 只保留订单生命周期、后台提交和结果落库；不再内嵌风险阈值和 provider 选择。

- `orchestrator.py`：维护批次、剩余待降低量、全文复检、早停和预算；
- `app/humanizer/llm_based.py`：只接收已经生成的定向任务并完成文本改写，不自行决定风险阈值和下一步链路。

这样可把“检测结果”和“改写执行”解耦，避免在接口层散落阈值判断。

### 4.5 改写任务执行

修改 `app/helpers/tasks.py` 的 `rewrite_and_analyze` / `do_background_rewrite`：

1. 读取原文 `turnitin_fit_detector_v2` 结果；若已有 `/api/analyze` 缓存则不重复检测。
2. `protect` 直接写入完成结果，保留订单记录，实际改写扣费词数为 0。
3. `low_cost_first` 先调用翻译链，完成后用 `turnitin_fit_detector_v2` 复检；只有触发失败条件才调用 Huma。
4. `huma_first` 先按结构块调用 Huma，再做 `turnitin_fit_detector_v2` 复检。
5. 复检结果写入统一结构；保留每个块的实际链路和升级原因。
6. 全文复检仍是最终展示分数，段落分数只用于定位和审计。
7. 首轮全文复检仍高于或等于 20% 时，调用归因策略并按 2 块一批执行低成本 LLM 二改；每批重新全文检测，达标立即停止。
8. 二改达到批次数、块次数或词数预算后仍未达标时，保留检测分数最低且内容校验通过的版本，不自动无限重试，也不自动再次全量调用 Huma。

原有 `HUMANIZER_FALLBACK_ADAPTER` 只表达“服务失败兜底”；风险分档由 `REWRITE_ROUTING_POLICY` 和 `REWRITE_TRANSLATION_ADAPTER`、`REWRITE_HUMA_ADAPTER`、`REWRITE_LLM_ADAPTER` 表达。

## 5. 成本与效果预估

### 成本

- 新增 `turnitin_fit_detector_v2` 本地推理：服务器 CPU 和模型加载内存成本；无按词付费，适合放在每次任务的第一层。
- `<20` 档：预计节省 100% 改写调用费用。
- `20–60` 档：默认只有翻译链成本；按实验规则，未达标样本才产生一次 Huma 费用。
- `>60` 档：与当前 Huma 主链路接近，增加一次本地复检但不增加外部检测费用。
- 首轮组合策略未达标：只对少量高贡献块调用低成本 LLM；以每单二改词数和批次数为硬预算，不能无上限追逐分数。
- 增加模型预热、超时和进程级分类器缓存；多 worker 部署允许每个 worker 各加载一次，但同一 worker 内不能重复加载。

### 响应时间影响

会增加，但主要增加在本地检测，不是改写 API 本身：

| 场景 | 新增步骤 | 预计新增耗时（暖机、单机） | 控制方式 |
|---|---|---:|---|
| 全文 `<20` | 1 次全文 `turnitin_fit_detector_v2` | 约 0.1–1 秒 | 模型常驻内存；命中后直接结束 |
| 全文 `20–60` | 全文检测 + 现有改写 + 复检 | 约 0.2–2 秒本地计算 | 原文结果缓存；翻译链与复检按现有后台任务执行 |
| 短文 `>60` | 全文检测 + 现有 Huma + 复检 | 约 0.2–2 秒本地计算 | 不做块级 `turnitin_fit_detector_v2`，避免小段逐个推理 |
| 长文 `>60` | 全文检测 + 批量块级 `turnitin_fit_detector_v2` + 改写 + 全文复检 | 约 0.5–3 秒本地计算 | 一次批量推理所有块，不逐块启动 Python 进程；只对可信正文块路由 |
| 首轮未达标 | 归因 + 每轮2块定向二改 + 每轮全文复检 | 每轮约增加一次低成本 LLM 延迟；本地归因与复检通常低于1秒 | 默认最多2轮、达标早停，减少不必要的全量二改 |

当前开发机实测：每次重新读取模型时，长短文检测中位数约 116–151ms；复用已加载模型后，同批 `predict_proba` 中位数约 32–33ms。以上仍需在阿里云上记录 P50/P95。禁止“每个块重新读取模型并串行等待”；模型常驻后，多轮本地复检相对网络改写延迟很小。

模型加载应放在 worker 首次初始化阶段，推理接口接收一批块并一次返回结果。定向二改的“每批2块”首先表示每两个块设置一个全文复检检查点；第一版继续服从现有改写器并发、最小请求间隔和限流，不为了二改另开无约束并发。后续只有在上游明确支持时才并行这两个请求。前端在原有 `detect`、`route`、`rewrite`、`detect_again` 基础上增加 `targeted_rewrite` 阶段，展示“正在优化剩余高风险内容”，不显示原始特征名和内部归因数值。

定向二改不一定增加订单总时长。以本地已有 P01 订单为参考，2,937 词、33 块的完整链路约 76.8 秒；如果归因早停只需处理约 12 块，即使增加数次低于 1 秒的本地复检，仍可能明显短于重新处理全部 33 块。实际收益取决于二改每块的网络耗时和成功率，灰度时必须分别记录“首轮耗时、归因耗时、各二改批次耗时、总耗时”。

### 效果

- 低风险文本减少无效改写，降低“原本低风险、改写后升高”的负资产情况。
- 中风险文本优先测试低成本翻译链，符合实验中其对 `turnitin_fit_detector_v2` 的明显降幅；若失败再升级，控制质量风险。
- 高风险文本继续使用 Huma，保持当前 `turnitin_fit_detector_v2` 评估中最稳定的主路线。
- 通过改写后 `turnitin_fit_detector_v2` 复检和失败升级，避免“调用完成但没有实际改善”。

以上耗时是方向性预估。当前 Phase 0–4 的代码与自动化回归已经完成，用户决定先按 `<20 / 20–60 / >60` 阈值上线；因此本次发布不再等待 50–100 篇影子样本。上线后仍需把前 50–100 篇真实订单作为首轮校准集，持续记录达标率、provider 命中、额外时延和成本，在数据足够前不调整阈值。

## 6. 实施分期与验收

### Phase 0：接口封装（已完成）

- 将 `turnitin_fit_detector_v2` 脚本封装为可导入函数。
- 增加 `turnitin_fit_detector_v2` adapter、mock、统一返回结构和进程级分类器实例缓存。
- 增加结构感知的检测专用重聚合；单元测试覆盖正常文本、极短文本、模型缺失、首次低 coverage、重聚合成功和重聚合后仍不足。

### Phase 1：影子路由（由既有实验与自动化场景替代）

- `/api/analyze` 同时保留现有检测结果，后台计算 `turnitin_fit_detector_v2` 但不改变实际改写链路。
- 记录拟议档位、拟议链路、coverage、耗时和预估费用。
- 与现有 Sapling/线上结果按样本对比，不取平均值。

### Phase 2：低风险保护 + 中风险翻译优先（已完成）

- 开启 `<20` 原文直出。
- 开启 `20–60` 翻译链优先、失败升级 Huma。
- 增加改写后 `turnitin_fit_detector_v2` 复检和自动升级；保持人工开关可快速回退到旧链路。

### Phase 3：高风险长文的段落级路由（已完成）

- 开启 `>60` 长文的结构化分段、段落级 `turnitin_fit_detector_v2` 和按段落风险分流；短文仍采用 Huma 全量首轮。
- 增加段落路由后的全文 `turnitin_fit_detector_v2` 复检和逐块贡献记录，但本阶段不自动二改。
- 增加长文、短文、DOCX 回填和失败重试回归测试。

### Phase 4：归因与定向二改（已完成，效果持续优化）

- 接入已经验证可重建模型分数的决策路径归因，只对首轮组合策略后仍 `>=20` 且覆盖率可信的订单启用。
- 增加 `AttributionPolicy`，把最多 3 个推高特征转换为定向 LLM 指令，并把最多 3 个压低特征转换为保护约束；规则本身不直接改正文。
- 默认每轮 2 块、最多 2 轮；第 2 轮仅在当前最佳分数为 `[20%, 30%)` 时执行，同一块最多尝试 2 次，每轮完成后拼回全文复检并早停。
- 增加数字、引用、公式、专有名词、段落数和词数偏移校验；失败候选不覆盖当前最佳版本。
- 灰度记录实际加权收益、LLM 费用、批次数、P50/P95 延迟和最终达标率，再决定是否调整批次大小与停止阈值。

### 验收门槛

- `turnitin_fit_detector_v2` 本地检测失败时，系统仍能按配置回退，不阻塞订单。
- `<20` 档不调用任何改写 API。
- `20–60` 档翻译链成功时不调用 Huma；失败或复检不达标时最多升级一次。
- 首次 `coverage <60%` 时自动执行且只执行一次结构化检测聚合；聚合后仍不足时不得进入强路由或自动二改。
- 同一个 worker 生命周期内模型文件只读取一次；全文检测、块检测、归因和复检复用同一模型版本。
- 二改默认最多 2 轮，同一块最多 2 次；实际全文分数 `<20` 后不再调用任何改写器，当前最佳分数 `>=30%` 时不执行第 2 轮。
- 二改输出未通过内容保护校验时保留此前最佳结果，不把异常候选交付给用户。
- 所有订单能追溯检测器、模型版本、coverage、风险档位和实际链路。
- 上线后的首轮 50–100 篇真实订单不降低原有完成率，并能统计外部改写 API 词数消耗变化。

## 7. 当前实施参数

以下参数已进入当前代码实现，后续根据灰度数据调整：

| 参数 | 当前值 | 设计说明 |
|---|---|---|
| 最终停止阈值 | 实测全文 `<20%` | 可以后续改为 `<18%` 留出检测波动余量，但会增加改写量 |
| 二改批次大小 | 每批 2 块 | 每块都复检延迟更高；一次选太多块会产生不必要调用 |
| 最大二改轮数 | 2 轮 | 每轮拼回全文复检，防止长尾订单无限重试 |
| 单块二改次数 | 最多 2 次 | 第一次未达标时允许基于当前最佳版本重新归因后再尝试一次 |
| 二改执行器 | 配置的低成本 `llm_based` | 规则只生成指令和做保护校验，不直接重写正文 |
| 归因输入 | 当前最佳块 + 不可修改实体 + 最多3个推高特征 + 最多3个保护特征 | 同时告诉 LLM 应该改什么和不能破坏什么 |
| 低覆盖重聚合 | `coverage <60%` 触发一次 | 聚合后仍不足则 `needs_review`，不循环改变块边界 |
| 检测聚合范围 | 同一正文区域内相邻短段 | 不跨标题、参考文献或特殊节点；不改变改写块和回填映射 |

成本约束需要确认采用哪一种口径：

1. **建议：整体平均成本不高于旧版全量 Huma。** 低风险保护、翻译链和首轮按块分流节省的预算，用于少数首轮失败订单的低成本 LLM 二改；逐日监控每千词平均成本并设置总预算熔断。
2. **更严格：每个订单都不高于旧版全量 Huma。** 每单二改预算只能来自该订单首轮未使用 Huma 的词数；如果首轮已经全量使用 Huma，则不再自动二改。这会限制 P03、P06、P16 这类“Huma 后接近达标”的救回空间。

文档检测口径还需要在实现前固定：建议只把可改写普通正文纳入路由分数，标题、参考文献、代码、表格占位等保护节点仍保存但不参与路由。这样检测目标与实际能改写的范围一致，也能避免 P01 的参考文献影响正文二改优先级。若产品最终展示必须包含全部节点，则需同时保存“正文路由分”和“完整展示分”，不能混成一个字段。

## 8. 暂不做的事项

- 不把 `turnitin_fit_detector_v2` 分数改名为 Turnitin 官方 AI 率。
- 不把 `turnitin_fit_detector_v2`、Sapling、aidetector 分数简单平均成一个“综合分”。
- 不在同一次请求中自动轮询多个外部网站检测器。
- 不在覆盖率不足或文本过短时强行给出确定风险档位。
- 不在本方案阶段直接替换线上 Sapling 的所有历史报表口径；历史订单继续保留原检测器字段。
