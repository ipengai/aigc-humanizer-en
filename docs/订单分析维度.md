# Huma 订单分析维度

订单表同时保留业务、输入、改写链路、效果和异常维度。新字段由应用启动时的 `Order.init_table` 自动补充；不直接修改线上数据库文件。历史订单缺失的字段保持为空，不根据旧数据猜测回填。

## 字段口径

| 维度 | 字段 | 说明 |
| --- | --- | --- |
| 改写配置 | `mode` | 用户选择的改写强度：`low` / `median` / `high` |
| 改写方法 | `rewrite_method` | 计划和实际使用的方法：`api` / `llm` / `rule` / `hybrid`；执行前先记录，成功后按实际链路更新 |
| 实际链路 | `humanizer_backend` | 实际执行路径，例如 `ai_text_humanizer->llm_based` |
| 引擎信息 | `humanizer_primary`、`humanizer_fallback`、`rewrite_provider`、`rewrite_model` | 主备引擎及实际服务商、模型 |
| 降级情况 | `fallback_used`、`fallback_block_count`、`rewrite_block_count` | 是否降级、降级块数、总改写块数 |
| 版本 | `rewrite_pipeline_version` | 用于比较不同算法版本的效果 |
| 输入方式 | `input_type`、`original_format` | 粘贴或上传，以及 TXT / DOCX 等格式 |
| 文档结构 | `original_paragraph_count`、`original_heading_count`、`original_table_count`、`original_reference_count` | 原文结构复杂度 |
| 输出结构 | `rewritten_paragraph_count`、`rewritten_heading_count`、`protected_paragraph_count`、`heading_count_changed` | 改写后的结构变化与受保护段落 |
| 效果 | `original_score`、`rewritten_score`、`detector_backend`、`rewritten_word_count`、`word_count_change_ratio` | 系统检测结果和篇幅变化 |
| 性能与异常 | `processing_duration_ms`、`failure_stage`、`failure_code` | 处理耗时、失败阶段和错误类型 |
| 获客来源 | `traffic_source`、`utm_source`、`utm_medium`、`utm_campaign`、`referrer_domain` | 渠道归因；仅保存来源域名，不保存完整来源链接 |

## 分析建议

- 按“改写方法 × 改写强度 × 检测平台”比较改写后 AI 率和低于 20% 的比例。
- 单独分析发生降级的订单，判断问题来自主引擎、备用引擎还是文档分块。
- 按输入格式、篇幅和结构复杂度观察错乱、标题丢失与用户反馈。
- 对外投放链接统一添加 UTM 参数，否则直接访问只能归为 `direct`。
